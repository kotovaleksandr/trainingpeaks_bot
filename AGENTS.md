# Инструкции для агентов

## Проект

TrainingPeaks Bot — Telegram-бот на Go, который отслеживает тренировки в
TrainingPeaks и отправляет уведомления и сводки тренировок.
Модуль: `github.com/kotovaleksandr/trainingpeaks_bot`. Версия языка в `go.mod` —
Go 1.27.1. Весь код находится в корне, в пакете `main`.

## Карта кода

- `main.go`: запуск, Telegram-команды, расписание, уведомления, форматирование
  сообщений, интерфейсы `sender` и `tpclient`, состояние `appState`.
- `tpclient.go`: HTTP-клиент TrainingPeaks, модель `Workout`, разбор дат,
  выборка тренировок, сравнение наборов и обновление токена.
- `config.go`: загрузка конфигурации и сохранение отдельных полей.
- `config.example.json`: пример конфигурации; `README.md`: пользовательская
  документация, команды и запуск.
- `tpclient_test.go`, `botmock.go`, `clientmock.go`: тесты и тестовые двойники.
- `data_samples/`: JSON-фикстуры тренировок.
- `Dockerfile`: основной образ; `Dockerfile.arm`: отдельная ARM-сборка.
- `.github/workflows/docker-image.yml`: сборка и публикация в GHCR для
  `linux/amd64` и `linux/arm64` при push в `main` или ручном запуске.

## Изменения

- Делай изменения в рамках задачи, сохраняя существующую структуру проекта.
- Не меняй версию Go, `go.mod` и зависимости без согласования с пользователем.
  Используй возможности Go 1.27.1; не добавляй зависимости ради тестовых утилит.
- Форматируй изменённый Go-код через `gofmt`, импорты — через `goimports`,
  если инструмент установлен.
- Предпочитай ранний возврат, обрабатывай ошибки, начинай тексты ошибок
  со строчной буквы. Не редактируй сгенерированные файлы.
- При изменении интерфейсов обновляй все реализации и тестовые двойники.
- Для новых или изменяемых исходящих запросов задавай явный таймаут;
  передавай `context.Context` первым параметром, когда он нужен.
- Синхронизируй доступ к общему состоянию. Не удерживай mutex во время
  сетевого запроса и не изменяй общий срез без защиты.
- Обновляй `README.md` и пример конфигурации при изменении пользовательского
  поведения или настроек. В примерах используй только фиктивные значения.

## Поведение, которое нужно учитывать

- Опрос тренировок выполняется раз в 10 минут, обновление токена — раз в 9 минут.
- Ежедневный дайджест отправляется в 19:00 по Москве; недельный план —
  по понедельникам в 19:00 по Москве.
- Команды: `/today`, `/week`, `/digest`, `/plan`. `/week` показывает остаток
  недели, `/plan` — неделю целиком с понедельника по воскресенье.
- Для календарной логики используй `moscowLocation()` и `AddDate` для дней.
  Проверяй границы дня и недели, включая воскресенье и понедельник.
- `CompareTwoSets` сообщает о новых и изменённых тренировках; удаление
  тренировки не считается изменением для уведомления.
- При нулевом `tp_user_id` бот определяет спортсмена через API;
  при нулевом `telegram_chat_id` работает обнаружение chat ID.
- Текущая реализация сохраняет обновлённый токен и chat ID в `config.json`.
  Учитывай побочные эффекты запуска и записи конфигурации.

## Проверка

Команды выполняются из корня репозитория:

```sh
go build ./...
go vet ./...
go test ./... -run '^$'
```

Последняя команда компилирует тесты без выполнения. Для выбранных автономных
тестов используй явный список, например:

```sh
go test ./... -run '^(TestFindNewWorkout|TestFindChangedWorkout|TestWorkoutDeleted)$'
```

- Не запускай полный `go test ./...` как автономную проверку: существующие
  `TestGetDataFromServer` и `TestRefreshToken` используют реальные API и файл
  учётных данных `tp_token`. `TestRefreshToken` также выводит полученный токен.
  Перед полным прогоном эти тесты нужно изолировать и убрать вывод секрета.
- Новые unit-тесты должны быть автономными: используй тестовые двойники и
  фикстуры без реальных токенов, Telegram-сообщений и внешних API.
- Для изменений конкурентного кода запускай подходящие автономные тесты
  с `-race`. В независимых тестах используй `t.Parallel()`, в помощниках —
  `t.Helper()`.
- Makefile и настроенного `make lint` сейчас нет; не выдавай эту команду
  за существующую проверку проекта.
- Для изменений только документации проверь содержание и ссылки;
  сборка и тесты обычно не требуются.

## Секреты и внешние действия

- Не читай и не выводи реальные `config.json`, `tp_token`, `telegram_token`
  и другие файлы учётных данных. Не обращайся к `.env`, `.env.*`, `.idea`
  и чувствительным каталогам пользователя.
- Не добавляй секреты в код, примеры, тесты, логи или коммиты. Для новых
  механизмов хранения секретов используй Vault.
- Не запускай бота для проверки кода: запуск обращается к реальным API,
  может отправлять сообщения и перезаписывать конфигурацию.
- Отправка сообщений, публикация образов и другие внешние изменения требуют
  соответствующего разрешения в задаче. Для локальной проверки достаточно
  сборки и автономных тестов.
